## 0d. Schema v4: migration from the shipped v3 schemas

**Problem (confirmed):** at `70d3b54`, `schemaVersion` was still 3, but `match_candidates` and `held_group` had been added inside `if (from < 3)` after v3 had already shipped in review builds. An existing v3 database never runs that block again. Reproduced with **real old-v3 databases generated by the code of the shipping commits** (`test/fixtures/db/v3_<commit>.db` plus a `.json` manifest of their contents):
- **`v3_15700e1.db`** (no `match_candidates`, no `held_group`): **every ingestion failed** with `SqliteException: no such column: match_candidates`.
- **`v3_5b7d6fc.db`** (`match_candidates`, no `held_group`, with one held capture): normal capture worked, but grouping a re-delivery failed with `no such column: held_group`.

**Fix:** `schemaVersion = 4`.
- The `from < 3` step is back to exactly what shipped in v3: `counter_last4`, the duplicate rename and the unique index.
- The new `from < 4` step adds `match_candidates` and `held_group`, each only if missing. It's additive: no row is rewritten or deleted.

**Test:** `test/core/schema_v4_upgrade_test.dart`, one test per fixture, both passing. Each test copies the real old file and opens it with the current code, then checks:
- `user_version` is 4, all three columns are present, and the unique index exists;
- **row counts of 9 tables match the manifest**, and so does the expense total;
- the capture held by the old build resolves with **Separate purchase** (+1.500 once; a second tap is a no-op);
- a replay of an old platform ID is `duplicate`;
- a new ambiguous settlement is held, a cross-source re-delivery joins its `held_group`, and **Same transaction** settles the chosen authorization and resolves the grouped re-delivery; a late Dismiss is refused;
- after reopening, there is no second migration and nothing is lost.

The household v1→v2 and v2→v3 migration tests now expect the current version.

**Full run (3 consecutive):** `FILS_E2E_API=… flutter test test/core test/e2e` → **182 passed, 0 failed**, each time. `flutter test test/perf` run separately → passed each time (insert20k = 16.1–17.4 s, budget 20 s). `flutter analyze` → 0 errors, 0 warnings.

**Perf note:** one full run that included `test/perf` in parallel with everything else exceeded the 20 s insert budget (20.5 s). The same perf test on the original code (`0be447d`) measures 14.8–18.1 s on this container today, the same as now, so there is no regression. The budget wasn't loosened; perf is run on its own.

## 0c. Codex review, round 4: held-group identity and the settlement predicate

**Fix** (`ingestion.dart`, schema v3 column `source_events.held_group`):
- Captures are grouped only through **explicit membership**. A held capture joins another only when both resolve to the **same known account** and their banks don't conflict (`_sameVerifiedAccount`). Unknown identity on either side means no join.
- Same, Separate and Dismiss resolve **only members of that group**, re-verifying each member's account first. The text-hash bulk update is gone.
- `_isSettlementOf` now requires the incoming message to be a **posted purchase**. The ingest path and `confirmSameTransaction` share this predicate.

**Results:** `held_identity_test.dart`, 10 tests, all pass:
- 6 cross-bank cases (Same, Separate, Dismiss × act on NBK or on KFH). Each checks the other capture's status, raw text, candidates, notes and every transaction on its account, then that it can still be resolved on its own.
- Same bank with conflicting accounts.
- A genuine same-account re-delivery is still grouped.
- **Shortcut repeat → Same → still pending at 10.000**, then the real settlement: **exactly 1 transaction, posted, 11.000** (spending 11.000, not 21.000).
- A second pending authorization never settles the first.

**Also fixed:** a pre-existing flaky assertion in `test/e2e/backend_sync_e2e_test.dart`. It used `expect(() => api.pull(null), throwsA(...))` without `await` and recorded consent immediately after, so it intermittently raced (1 failure in about 8 runs). It is now `await expectLater(...)`; 8 out of 8 isolated runs pass.

## 0b. Codex review, round 3: ambiguous settlement and conditional Dismiss

**Reproduction on `e81f2d7`:** a throwaway repro test, not committed because its Dismiss case deliberately calls the old UI statement from `review_screen.dart:247-249`. Its scenarios are carried into the regression tests below.

| Finding | Repro | Before |
|---|---|---|
| 1. Settlement picks the first authorization | Pending 10.000 and 12.000 (same merchant and account), then settlement 11.000 | `settledPending` (applied to the first match) |
| 1. Cross-source re-delivery | The same settlement via a notification | **Settled the other authorization** too (0 pending left) |
| 2. Unconditional Dismiss | Separate, then the UI Dismiss statement | Status overwritten from `posted` to `ignored` (the transaction stayed, the event said ignored) |

**Fix** (`ingestion.dart`, `review_screen.dart`):
- **Settlement:** every qualifying authorization is collected (`_isSettlementOf`). Exactly one is settled. More than one means the settlement is **held** with all of them as candidates. **Same transaction** settles exactly the chosen one, in one database transaction, and only an offered candidate is accepted.
- **Re-deliveries:** a re-delivery of the same text through another channel is never applied as a second settlement. If the original is held, the re-delivery is held with it and resolved (or dismissed) together. If the original was already applied, the re-delivery merges into the record it produced.
- **Dismiss:** now `IngestionService.dismissHeld`, a conditional `status = held` update inside a transaction. It returns whether it applied, and the UI shows "Already resolved" otherwise.

**Regression tests:** `test/core/settlement_dismiss_test.dart` (12 tests):
- Hold, with both candidates offered.
- Choosing an authorization settles exactly that one, under a crash mid-resolution, a retry, the other choice and a restart.
- A transaction outside the suggested set is refused.
- Re-delivery after resolution and while held.
- Separate purchase.
- A single qualifying authorization still settles directly.
- Dismiss in both orders against Same and against Separate, and Dismiss resolving a held re-delivery.
- **Competing connections:** two `AppDatabase` connections on one file in WAL mode, 24 races (Dismiss vs Separate and Dismiss vs Same, both issue orders). The results were *dismiss won 12, resolution won 12*. No race ever produced a dismissed event with a transaction, or a resolution overwritten by a dismissal.

**Full run:** `FILS_E2E_API=… flutter test test/core test/perf test/e2e` → **171 passed, 0 failed**, three consecutive runs. An earlier run showed 3 E2E failures only because the local backend process had stopped (health check `000`); after a restart, all passed. `flutter analyze` → 0 errors, 0 warnings.

**TestFlight prep:** added `PrivacyInfo.xcprivacy` to Runner and ShareExtension, declaring only the required-reason API used by our own Swift code (file timestamps, `C617.1`, in `CaptureInbox.swift`). The archive check now verifies both are bundled.

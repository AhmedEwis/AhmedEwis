# Fils practical threat model

The structure is STRIDE-style: each threat lists what could go wrong, the control actually
implemented (with file references), and the remaining risk. Paths are relative to `fils/`.
Statements describe the code as of this commit. "Planned" means it is not implemented.

Assets: the user's financial history (on-device and synced), session tokens, provider secrets,
billing entitlements and household membership.

| # | Threat (STRIDE) | Implemented controls | Residual risk |
|---|---|---|---|
| 1 | **Device theft or loss** (Information disclosure) | The local DB is encrypted with SQLite3MultipleCiphers. A random 256-bit key is stored in Keychain/Keystore with `first_unlock_this_device` (never backed up or migrated) (`mobile/lib/data/db/open.dart`, `pubspec.yaml` `hooks.user_defines.sqlite3.source: sqlite3mc`). Session tokens live in secure storage with the same accessibility (`mobile/lib/data/api/api_client.dart` `TokenStore`). An optional biometric app lock gates the UI. Remote session revocation is available (`DELETE /v1/me/sessions/{id}`, `backend/fils_api/routers/me.py`). | An unlocked, stolen phone exposes the app unless the biometric lock is on. The biometric lock is a UI gate, not the encryption key. After first unlock, a forensic attacker with OS-level compromise could read the key. |
| 2 | **Cross-user data access** (Elevation of privilege) | Every API dependency resolves the user from a session-checked access token (`backend/fils_api/security.py`). Sync reads and writes are scoped to the user plus their household memberships. Referenced ids must belong to the same scope (`backend/fils_api/services/sync.py`, `sync_schemas.py` `REFERENCES`). Tests cover cross-user pull and push attempts and household removal (`backend/tests`). On the device, assistant tools run only on the local user's snapshot (`mobile/lib/core/assistant/tools.dart`). | Logic bugs in new endpoints. Keep the cross-user tests mandatory in CI (`.github/workflows/backend-ci.yml`). |
| 3 | **Malicious imports** (CSV/PDF/images, Tampering / DoS) | Uploads are validated by magic bytes, not the declared type, with a 10 MB size limit and a request body limit (`backend/fils_api/services/uploads.py`, `middleware.py`). The CSV parser caps rows (`services/documents.py` `MAX_ROWS`). Uploads are AES-GCM encrypted at rest and deleted after extraction; candidates are purged after 24 h (`services/blobs.py`, worker retention). Exports escape spreadsheet formula prefixes (`services/exporter.py`). Extracted rows come back for preview and correction, never auto-posted. | A malformed PDF could exploit a parser bug (pypdf). It runs in the worker container without secrets beyond the DB URL; consider sandboxing. |
| 4 | **Replayed or duplicated ingestion** (Tampering) | The device dedupes by platform id per source (replay) and treats the same text across SMS and notification as one event. Wallet and bank SMS events are matched semantically. Identical texts are flagged for review, never dropped silently (`mobile/lib/data/ingestion.dart`, tests in `mobile/test/core/ingestion_test.dart`). The server has idempotency keys (`backend/fils_api/middleware.py`): same key and body replays the stored response, a different body returns 409. Sync batches use a content-derived idempotency key (`mobile/lib/data/sync/sync_engine.dart`). | A genuinely duplicated SMS with no platform id goes to review; the user decides. |
| 5 | **Exposed secrets** (Information disclosure) | No secrets live in the app. Speech tokens last about 10 minutes and LLM calls are proxied (`backend/fils_api/routers/voice.py`, `assistant.py`). Backend secrets come from Key Vault references through a managed identity (`infra/azure/modules/containerapps.bicep`, `keyvault.bicep`). Staging and production refuse to start without `FILS_JWT_SECRET` and `FILS_DATA_KEY` (`backend/fils_api/config.py`). `.env.example` contains no values. The gitleaks workflow runs in CI (`.github/workflows/security.yml`). ACR has the admin user disabled, and Storage has shared-key access disabled. | An operator workstation compromise during `deploy.sh secrets`. Use PIM and short-lived roles. Rotation procedure: `docs/deployment.md`. |
| 6 | **Account takeover** (Spoofing) | Apple and Google ID tokens are verified against JWKS (iss, aud, exp, signature) with single-use, server-issued nonces (`backend/fils_api/providers/identity.py`, `routers/auth.py`). Access tokens are short-lived (15 min). Refresh tokens rotate, and reuse revokes the whole session family and is audit-logged (`routers/auth.py`). Sensitive operations (export, delete, identity linking) require a reauth token (5 min). Accounts are never linked by matching email. Rate limits apply to auth routes. | Compromise of the user's Apple or Google account itself. Rate limits are per replica (README note). |
| 7 | **Prompt injection** (via SMS, merchant names, documents) | Deterministic parsing comes first. The LLM extraction result is accepted only if each field's evidence substring appears in the input and the amount parses from it; OTPs are blocked before the model (`backend/fils_api/routers/ingest.py`, `services/textguard.py`). The assistant system prompt marks tool results as untrusted, and undeclared tool calls are dropped (`routers/assistant.py`). All numbers come from device tools (`mobile/lib/core/assistant/tools.dart`). Merchant-name injection test: `mobile/test/core/assistant_test.dart`. | Injected text containing a real-looking amount that is also present in the message can be extracted. The device must route low-confidence AI results to review (noted by the backend owner). The LLM can phrase text misleadingly, but cannot change numbers. |
| 8 | **Malicious household invitations** (Spoofing / EoP) | Only the owner invites. Codes are random, stored as SHA-256 hashes, single-use, expiring (1–336 h) and revocable (`backend/fils_api/routers/households.py`). Viewers cannot push. Transactions are never shared automatically; sharing is explicit per record. Removal immediately cuts access to household-scoped records. | Social engineering: a user sharing a code with the wrong person. The code still only grants the role chosen, and the owner can remove members. |
| 9 | **Payment webhook spoofing or replay** (Spoofing / Tampering) | Apple notifications are JWS verified with the x5c chain against the pinned Apple Root CA G3, and replays are rejected by `notificationUUID` (`backend/fils_api/services/apple_jws.py`, `routers/billing.py`). Google RTDN Pub/Sub push requires a valid Google OIDC JWT with the configured audience and service account; purchase state is re-fetched from the Play API and never trusted from the message (`services/google_play.py`). Purchases are bound to the account (`appAccountToken` / `obfuscatedExternalAccountId`), and one purchase can't unlock two accounts. | Until the Apple root cert and Play credentials are configured, billing endpoints return 503. That fails closed. |
| 10 | **Sensitive data in logs or crash reports** (Information disclosure) | Structured JSON logs redact bearer tokens, keys and secrets, emails, and message text; the default uvicorn access log is replaced by a redacted one (`backend/fils_api/logging_setup.py`). The device never logs raw SMS. OTP text is never stored. Raw text is kept only for review items and purged after 30 days (`mobile/lib/data/ingestion.dart`, `store.purgeExpiredRawText`). App Insights IP masking stays on (`infra/azure/modules/monitoring.bicep`). | Third-party crash SDKs are not yet integrated. Configure scrubbing before adding one. |

## Additional controls

- **Transport:** TLS only. Container Apps ingress sets `allowInsecure: false`, and Postgres sets
  `require_secure_transport=on`. Postgres has no public endpoint (VNet-delegated subnet and private
  DNS).
- **Production hardening:** no `/docs` and no demo endpoint in production. CORS is off by default.
  Security headers are set (`middleware.py`).
- **Account deletion:** sessions are revoked immediately and a background job hard-deletes all user
  rows (`routers/me.py`, `worker.py`). The app also wipes the local DB and its key.
- **Encryption claims:** the server can read synced data. It is encrypted at rest by Azure, but
  **not end-to-end encrypted**. The privacy notice says so.
